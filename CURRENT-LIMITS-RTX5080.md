# Generation-gated current-limit controls

Druta's Control tab discovers current limits from a generation descriptor plus
the live driver ABI. Slider eligibility never depends on a PCI device ID,
board name, driver string or VBIOS. Pascal and Turing expose the validated
**Core current limit**; Blackwell additionally exposes **Other rail current
limit** when both returned policy descriptors validate.

| Generation / control | Driver default on tested card | Normal maximum | XOC maximum |
|---|---:|---:|---:|
| Pascal core, policy 13 | 204.700 A | 218 A | 218 A |
| Turing core, policy 13 | 350.780 A | 390 A | 390 A |
| Blackwell core, policy 13 | 300 A | 500 A | 5,001 A |
| Blackwell other rail, policy 14 | 120 A | 200 A | 5,001 A |

Values are displayed in amperes and passed to the driver in milliamps.
**Apply** changes one rail limit; **Stock** restores that policy's reported
default. Readouts show measured current and the effective limit. Normal
caps come from the backend row and apply in both the UI and backend. XOC uses
each policy's advertised API maximum, subject to the generation layout.

Turning XOC off does not rewrite the GPU. A previously applied higher value
remains visible and can be lowered, but cannot be raised further without
XOC. Named profiles capture the requested limits in exact milliamps, preserving
them when the effective ceiling differs; restoring a
profile uses the same backend bounds and does not enable XOC. Reset all to
stock restores every reported default.

The 5,001 A bound is an API request ceiling, not the GPU's physical current
rating. These limits are distinct from the ordinary board-power limit in
watts, so a current policy can limit clocks below the displayed board TDP.

## Measured acceptance

On NVIDIA driver **580.97**, the TITAN RTX (Turing) and TITAN Xp (Pascal)
policy 13 passed reversible idle production-backend tests in both directions:

- TITAN RTX: 350.780 A to 345.780 A and 355.780 A, then exact restoration.
- TITAN Xp: 204.700 A to 199.700 A and 209.700 A, then exact restoration.
- Every accepted value appeared in both the stored control GET and independent
  effective-policy GET. The complete control block matched its entry snapshot
  after every restore.
- Pascal/Turing policies 14 and 15 already report their maximum and do not
  match the validated core-current descriptor, so Druta does not expose
  them as current sliders. Their raw numbers are not additional amp controls.

The advertised upper boundaries were then tested directly on driver 580.97.
The TITAN RTX accepted 390.000 A but rejected 390.001 A; the TITAN Xp accepted
218.000 A but rejected 218.001 A. Both above-maximum requests returned RM
status `0x1F`, changed neither the stored nor effective limit, and were followed
by a verified replay of the original full policy record. Evidence is in
[`experiments/current-limit-ceiling-titan-rtx-20260908.json`](experiments/current-limit-ceiling-titan-rtx-20260908.json)
and
[`experiments/current-limit-ceiling-titan-xp-20260908.json`](experiments/current-limit-ceiling-titan-xp-20260908.json).

The public validation artifact is
[`experiments/current-limits-titan-20260908.json`](experiments/current-limits-titan-20260908.json),
generated by
[`experiments/validate_titan_current_limits_production.py`](experiments/validate_titan_current_limits_production.py).

On the ASUS RTX 5080 Astral, driver 580.97 and VBIOS 98.03.3b.c0.6f:

- Policy 13 accepted 295 A, 305 A and 5,001 A. A request for 5,001.001 A
  was rejected with RM status `0x1F`.
- Policy 14 accepted 115 A and 5,001 A. A request for 5,001.001 A was
  rejected with the same status.
- Accepted values appeared in both the control GET and separate effective
  dynamic-policy GET. Rejected boundary requests retained the previous limit.
- Every test restored the original full control block and effective limit.
  All upper-bound tests ran idle with FurMark stopped.

The production backend also passed an idle **305 A / 125 A** apply/readback/
restore check. Normal-mode requests for **500.001 A / 200.001 A** were rejected
without changing the control block. UI checks confirmed typed-value caps,
XOC ranges and retention of existing higher settings when XOC is disabled.

## Backend contract and ABI

The GTX 745 (Maxwell) and GTX 770 (Kepler) were also checked on driver
472.12. Neither exposes the modern current-policy interface, and their
legacy policy records do not establish usable current controls. Druta
therefore exposes no current sliders on these tested cards. See the
[Kepler/Maxwell report](CURRENT-LIMITS-KEPLER-MAXWELL.md) for read-only
captures and the limits of this finding.

`GPU.get_current_limits()` returns supported policies with `policy`, `label`,
`minimum_ma`, `normal_maximum_ma`, `maximum_ma`, `default_ma`, `limit_ma`, and
`value_ma`. `GPU.set_current_limit_ma(policy, ma)` applies a bounded request
and returns `(ok, message)`. Profile data uses `current_limits_ma` with string
policy IDs and integer milliamp values; older profiles remain compatible.

On the measured 580.97 ABI, control GET **0x2080a61a** and SET **0x2080e61b** use a **4432-byte** parameter
block. The selection mask is at **0x10**; records start at **0x14** with
**0x7c** stride. Policy 13 selects **0x2000**, with its limit at **0x664**;
policy 14 selects **0x4000**, with its limit at **0x6e0**. Blackwell current
records use type **0x12**; Pascal/Turing core current uses type **0x0b** and a
generation-specific channel. In all cases the metadata unit must identify mA.
The valid policy mask is read from the live info block (rather than assuming
Blackwell's `0x3ffff`) and must be echoed by control and dynamic GETs.

Writes preserve the freshly read control block and select only the requested
policy. Success requires matching control and effective dynamic readbacks.
An unknown generation or descriptor mismatch exposes no current slider.

### Driver 610.88 layout

The missing slider was reproduced on a TITAN RTX with driver **610.88** and
VBIOS **90.02.1e.00.02**. Architecture detection and policy 13's descriptor
still passed; the old transport capture rejected the driver's larger packet.
The other user's HOF-board TITAN has not been measured directly.

Druta selects between the two measured layouts using the captured power GET
packet geometry, without a driver-version or board-identity allowlist:

| Parameter layout | 580.97 | 610.88 |
|---|---:|---:|
| Power GET A612 bytes | 11,680 | 54,352 |
| Policy info A618 bytes | 8,620 | 20,000 |
| Policy status A619 bytes | 172,080 | 396,024 |
| Policy control A61A / E61B bytes | 4,432 | 13,840 |
| Info record base / stride | 0x58 / 0xE4 | 0xCC / 0xFC |
| Status record base / stride | 0x70 / 0x1454 | 0x9C / 0x1720 |
| Control record base / stride | 0x14 / 0x7C | 0x14 / 0xC4 |

The newer info, status and control type echoes agreed across all 12 active
policies (mask **0xEBBF**). Policy 13 remains type **0x0B**, channel **19**,
with limits of **1 A minimum, 350.780 A default and 390 A advertised maximum**.
Its limit word moves from **0x664** to **0xA0C**. The setter accepted a
same-value request and **350.780 → 349.780 → 350.780 A**; stored and independent
effective readbacks matched each request, and all other control words were
preserved. The full original control block was verified after restoration.
The 390 A boundary was not retested on 610.88.

The updated production backend separately passed the same 1 A reduction and
exact restoration. Its only changed control word was at 0xA0C. Building the
existing UI row from the live getter produced **Core current limit (A)** at
350.780 A, with a 1–390 A range and no policy-14 slider on this Turing card.

Evidence: [610.88 validation](experiments/current-limits-titan-61088-20260908.json).
On 472.12 this TITAN uses the older 0x208026xx commands, which at that validation remained outside
these two current-control layouts.

## Public reproduction evidence

### Current diagnostic build validation (2026-09-08)

`1.3.0-current-diag` adds the 472.12 transport (2612: 3548-byte
packet / 3480-byte parameters). Legacy info/status/control/SET commands are
20802618/20802619/2080261A/2080261B; parameter sizes are
5520/69148/2124/2124 bytes. Record base/stride pairs are
0x3C/0x84, 0x64/0x828 and 0x14/0x34. Status selection uses word 0,
whereas the modern status layouts use word 1. Control selection uses word 4.

Evidence combines an original TITAN 472.12 info capture (retained in
`tests/fixture_current_47212.py`), original GTX 770 status/control captures,
and static inspection of NVIDIA's 472.12 nvapi64.dll. DLL SHA-256:
`4b8f6048bdc9b74cde55a6eced3ee517ee83b013e0706477298feb9d28ca13c2`.
RVA 0x8FB91 supplies SET size 0x84C, RVA 0x8FB99 selects 0x2080261B;
RVA 0x25E875 confirms a 0x34-byte control stride with base 0x14.
The subsequent [local TITAN 472.12 live check](experiments/current-limits-titan-47212-20260908.json)
verified full-mask control GET and policy 13 SET: 350.780 A -> 349.780 A ->
350.780 A, including stored/effective readback and exact restoration of the
complete original control block. The local board uses VBIOS 90.02.1e.00.02;
the remote HOF PCB / newer VBIOS still needs its own confirmation. The setter preserves the complete getter block,
selects one policy, checks stored/effective readback and attempts restoration
if a dispatched write has an uncertain result.

This diagnostic build removes fixed board-channel and advertised-maximum
matches. A differing channel is labeled by policy and channel rather than
assuming it is the core rail. Normal requests use a 500 A core / 200 A other
envelope, intersected with API bounds; XOC uses the returned maximum.
Known geometry, generation/type semantics, mA units and consistent values
remain required. An unavailable expected policy has a disabled visible row
with a reason and Copy info button, rather than being silently omitted.
Help's device report also includes current-policy diagnostics.
