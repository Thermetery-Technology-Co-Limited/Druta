# The same GP106 on driver 572.83: a third native policy record size

On 2026-11-02 the Gigabyte GTX 1060 6GB qualified for 1.9.06 under driver
576.80 was re-tested on **572.83**, same board, same VBIOS
`86.06.4b.00.32`. Live power and the current sliders both went away again,
with `0x2080A61C` (the role INFO GET) refused with RM `0x1F`.

This is the companion to the
[576.80 qualification](pascal-gp106-live-power-20261102.md); only the
differences are recorded here.

## What changed

| | 576.80 | 572.83 |
| --- | ---: | ---: |
| A612 transport packet/parameters | 11740 / 11672 | **3676 / 3608** |
| Client INFO `2080A630` | 1160 | 1160 |
| Client CONTROL / SET `2080A632` / `2080E633` | 392 | 392 |
| **Role INFO `2080A61C`** | 232 | **220** |
| **Native INFO `2080A618`** | 8620, record 228 | **8236, record 216** |
| Native CONTROL `2080A61A` | 4432, `0x14` / `0x7C` | 4432, `0x14` / `0x7C` |
| Native STATUS `2080A619` | 171048, `0x68` / `0x1434` | 171048, `0x68` / `0x1434` |

Three blocks are identical and two are not. As on 576.80, nothing may be
carried across on the strength of the blocks that match.

## The role GET size is not an independent constant

The role parameter is a 4-byte semantic selector followed by exactly one
native policy INFO record, so its accepted size fixes that record's stride.
Every ABI measured so far agrees:

| Role INFO size | Native INFO record stride |
| ---: | ---: |
| 264 | 260 |
| 232 | 228 |
| **220** | **216** |
| 136 | 132 |
| 120 | 116 |

1.9.07 therefore derives the stride from the accepted role size rather than
carrying it as a per-table constant, and records it on the binding only when
it differs from that layout's usual record size. The derived value is not
trusted on its own: it still has to bind the role definition to exactly one
occupied native policy before anything uses it, which is the check that
would catch a wrong stride.

Sweeps on this adapter accepted exactly one size per block: client INFO 1160
of 512..2600, role INFO 220 of 4..2048, native CONTROL 4432 of 1600..14400,
native INFO 8236 of 4000..22000, and native STATUS 171048 of 4000..210000.
Everything else returned RM `0x1F`.

## Native INFO base

Searching every 4-byte base for a unique occurrence of the role definition
produced three candidates — 88, 304 and 520 — because 304 and 520 are the
same match shifted by whole 216-byte records. Only base 88 decodes every one
of the ten occupied policies coherently (`v30` table version, a known type, a
`0`/`1` unit, and `1 <= min <= rated <= max`); 304 and 520 read zeros for
policies 3, 4, 7 and 10. Base 88 also reproduces the exact policy table
576.80 reports for this board, including core current at type `0x0B`,
channel 11, 1000/86800/95000 mA.

## Status geometry re-solved, not assumed

Although the status size matched 576.80's 171048, the base and stride were
solved again from live data: of every `(base, stride)` with base 0..2048 and
stride up to 12000, exactly one makes all ten occupied policies' status type
bytes equal their info type bytes and keeps every effective value inside
that policy's own bounds. It came back `0x68` / `0x1434`, the same pair — but
the check was run rather than skipped.

## Reversible idle trials

The board's captured request was **200 W**, its ordinary maximum, set by the
owner before this session; every trial restored it.

| Trial | XOC | Result |
| --- | --- | --- |
| Power 190 W | no | exact readback, restored |
| Power 201 W | yes | exact readback, restored |
| Power 250 W | yes | exact readback, restored |
| Core current 95 → 94.2 A | — | accepted, effective limit verified |
| Core current 95.001 A | — | refused, no state change |
| Core current restore 95 A | — | effective limit verified |

Core current policy 13 reads 1/86.8/95 A; its captured 95 A request is the
value the driver derives from a board request at its 200 W maximum, not a
stored user setting. The native effective power limit reads 200000 mW,
matching the configured request. The complete captured client and native
state was restored and verified after every trial, with a hidden 30-second
restoration watchdog armed throughout.

Sanitized data: [pascal-gp106-driver57283-20261102.json](pascal-gp106-driver57283-20261102.json).

## Scope

Idle software observations on one adapter and two drivers. They do not
establish physical enforcement under load, behavior on other Pascal boards
or other drivers, or any change in actual power draw; nothing here was
measured with a power meter. The 1999 W XOC range remains a software request
envelope, and core current stays bounded by the adapter's own 95 A maximum.
