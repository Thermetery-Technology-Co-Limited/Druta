# The same GP106 on driver 472.12: a known ABI behind a generation gate

On 2026-11-02 the Gigabyte GTX 1060 6GB used for the 1.9.06 and 1.9.07 work
was tested on **472.12**, same board, same VBIOS `86.06.4b.00.32`. Live power
and the current sliders were unavailable again, but for a different reason
than on 576.80 or 572.83: nothing about the interface was unknown.

Companion to the [576.80](pascal-gp106-live-power-20261102.md) and
[572.83](pascal-gp106-driver57283-20261102.md) reports.

## Nothing new was measured

This driver presents the `20802612` RM26 transport at 3548/3480 bytes, which
Druta already described, and every block matched the existing
`RM26_EXTENDED_SIZES` table on the first try:

| Operation | Wire command | Parameter bytes | Accepted |
| --- | --- | ---: | --- |
| Client INFO | `20802630` | 900 | yes |
| Client CONTROL / SET | `20802632` / `20802633` | 388 | yes |
| Role INFO | `2080261C` | 136 | yes |
| Native INFO | `20802618` | 5520 | yes |
| Native CONTROL | `2080261A` | 2124 | yes |
| Native STATUS | `20802619` | 69148 | yes |

Sweeps confirmed each is the only accepted size: client INFO over 256..2600,
role INFO over 4..1024, native CONTROL over 512..8000, native INFO over
1024..12000 and native STATUS over 4000..120000.

Native INFO base `0x3C` with a 132-byte record binds role 1 to policy 2 and
decodes the same ten occupied policies this board reports on every other
driver, including core current at type `0x0B`, channel 11, 1000/86800/95000
mA. The role size rule holds here too: 136 = 4 + 132.

## The only blocker was a generation gate

`ClientPowerController._transport` refused both RM26 geometries on anything
but Turing:

> This client-power RM26 ABI requires Turing

That was an incremental record of which generations had been qualified, not a
property of the interface — the same shape as the client-group list 1.9.06
widened for Pascal. 1.9.07 replaces it with `RM26_ARCHITECTURES`, now
`(4, 6)`.

It is deliberately kept as a **separate** list from
`LEGACY_GROUP_ARCHITECTURES`, which is `(4, 6, 7)`. Merging them would claim
Ampere on the RM26 family, which nothing has tested. A generation qualified
against one packet family is not thereby qualified against the other.

## RM26 rejects a wrong size with RM 0x3A

Probing native STATUS at the sizes other transports use returned RM `0x3A`
on this family, not the RM `0x1F` the A6xx families return:

| Native STATUS parameter bytes | Result |
| ---: | --- |
| **69148** | **accepted** |
| 14148, 171048, 172080, 190272, 396024, 397048 | refused, RM `0x3A` |

This is recorded as an observation only. No code path changed on the strength
of it: the RM26 layouts are selected by the transport key and have a single
candidate each, so none of them probes sizes and none needs to classify
`0x3A`. Treating it as equivalent to `0x1F` elsewhere would be a guess about
a code whose meaning has not been established here.

## Reversible idle trials

Captured baseline 180 W; every trial restored it, with a hidden 30-second
restoration watchdog armed.

| Trial | XOC | Result |
| --- | --- | --- |
| Power 190 W | no | exact readback, restored |
| Power 201 W | yes | exact readback, restored |
| Power 250 W | yes | exact readback, restored |
| Core current 86.8 → 86 A | — | accepted, effective limit verified |
| Core current 95.001 A | — | refused, no state change |
| Core current restore 86.8 A | — | effective limit verified |

With XOC the slider range becomes 0.001..1999 W. The current-policy record
layout in use is info `0x3C`/132, status `0x64`/2088, control `0x14`/52, all
pre-existing. The native effective power limit reads 185625 mW against a
configured 180 W. Detailed arbitration stays unavailable on the RM26 layouts,
as before.

Sanitized data: [pascal-gp106-driver47212-20261102.json](pascal-gp106-driver47212-20261102.json).

## Scope

Idle software observations on one adapter across three drivers. They do not
establish physical enforcement under load, behavior on other Pascal boards or
other drivers, or any change in actual power draw; nothing here was measured
with a power meter. The 1999 W XOC range remains a software request envelope,
and core current stays bounded by the adapter's own 95 A maximum.
