# Manual PCIe speed request on RTX 5080 / 617.42

The documented PCIe speed command changed the source-bound target and both
endpoints' negotiated generation from 1 to 2 and back to 1. Width remained
x16. The complete observed target register and endpoint capability/control/status
words matched the captured baseline after return. This establishes a working
manual speed request on the tested configuration, not a permanent speed lock.

The adapter was an RTX 5080, VBIOS 98.03.3b.c0.6f, driver 617.42. Its GPU
reported a maximum generation of 5 and the upstream root port a maximum of 4.
Those values are observations, not product device or driver allowlists.

## Operation and witnesses

[NVIDIA's public header](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/ca2d03e6fafd4d4b56b383497d931c25b283bfcf/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080bus.h)
defines `NV2080_CTRL_CMD_BUS_SET_PCIE_SPEED` (`0x20801805`) with a four-byte
generation enum. The root trial sent exactly two requests: generation 2 and
generation 1. Both returned NT status zero, native completion and RM status
zero, with the requested payload unchanged.

The established `0x20801823` GET_INFO_V2 selectors 3/4 report GPU/root link
capabilities; selectors 7/8 report their control/status words. The trial checked
the full request envelope and independently decoded current generation and
width. A guarded GLOBAL READ32 operation through `0x20800122` read only
source-bound register `0x85008`; no raw register write was used.

| Observation | Register 0x85008 | Target generation | GPU/root generation | Width |
|---|---|---:|---|---|
| Two baseline reads | 0x80011060 | 1 | 1 / 1 | x16 |
| Immediately after request | 0x80021060 | 2 | 2 / 2 | x16 |
| After 50 ms and 250 ms waits | 0x80021060 | 2 | 2 / 2 | x16 |
| Before return request | 0x80021060 | 2 | 2 / 2 | x16 |
| Two returned reads | 0x80011060 | 1 | 1 / 1 | x16 |

The waits are intervals between reads, not latency measurements. All eight
observations and both native SET envelopes are in the [receipt](pcie-speed-5080-61742-20261105.json).
Root audited their original bytes, output-field geometry, requested-generation
changes and baseline restoration independently of the summary flags.

A second trial exercised the actual product panel's Request speed and Request
previous speed callbacks with the live backend. Both transitions were verified,
and the independent register and full endpoint-word observations matched the
baseline afterward. Its results and product source hashes are included in the
same receipt. Both trials were at idle on this one adapter.

## Source binding and scope

The saved 617.42 host driver SHA-256 is
`DB407B964C11441642A1642A0922C35990DE974C267A08537C3432765365F84B`.
The Blackwell bus callbacks traced through `972240`, `96C7C0` and `96C190`
establish a fallback that writes requested generation to `0x85008` bits 19:16,
encodes current width in bits 22:20, triggers training and checks current speed.
The x16 encoding is zero, matching the captured baseline. The existing GLOBAL
READ32 path joins the same register-access helper, device and instance.
The `+4F0` getter resolves to `96E9E0` and reads current speed, not the target.
Consequently an early success or a current-speed match alone cannot establish
a target change.

Another guarded host-message path exists; its receiver and runtime selection
remain unobserved. The live trial establishes the actual request/readback
behavior without claiming which internal branch executed. No firmware analysis
was performed.

Druta gates the understood register layout by architecture and validates fresh
endpoint capabilities, target identity and readback. It does not assume that
every source-supported generation works on every adapter. A successful command
without matching target and endpoint readback remains unverified. The driver
may subsequently change the link speed through its own power management.

No workload, physical power, throughput or long-term retention measurement was
performed. No registry changes, GPU restart or Windows reboot were needed.
Manual previous-speed requests are not automatic cleanup or startup replay.
Selective ASPM L1 and LTR remain separate, unqualified controls.

Private source captures and root scripts are under
`registry-overrides/pcie-speed-source-20261105` and
`registry-overrides/pcie-speed-root-20261105`.
