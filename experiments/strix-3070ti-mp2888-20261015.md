# MP2888A investigation on one ASUS Strix RTX 3070 Ti

Scope: one adapter, PCI 10DE:2482 / subsystem 880E1043, VBIOS
94.04.5a.00.56, driver 595.97. These identities record the test rig and are
not compatibility filters. Work starts from Druta tag 1.8.0, df57a9a.
The user authorized reversible core-voltage experiments up to 1200mV.

## Original failure and independent meter evidence

Discovery succeeds at port1/address0x20. Coarse VOUT_OFFSET23h writes read
back exactly, but the existing verifier cannot establish a voltage response
in the initial PWMVID configuration. E1h bit4 is clear, OPERATION=80h,
45h bit5 is clear, PAGE=0, and STATUS_BYTE78h reports the output active.

Early manual readings of 1.055/1.069/1.049V were taken while the GPU voltage
and operating point varied. An earlier interpretation called this a reversible
response; that conclusion was premature. A 0.674V reading after a timed hold
release is also excluded from the held-point comparison.

The user then applied Max it and held VID1093.75mV/core2145MHz. With that
steady request, the independent meter showed:

| Total23h offset request | Raw23h | Meter voltage |
| --- | --- | --- |
| 0mV | 0 | 1.096V |
| +25mV | 4 | 1.096V |
| +50mV | 8 | 1.099V |
| +75mV | 12 | 1.099V |

The user judged the 3mV movement within measurement error. These results do
not validate coarse offset control in that PWMVID operating configuration.
The provisional meter-assisted Verify workflow was therefore removed.

## Protocol and target checks

- Byte and word reads with optional PEC validated84/84 CRC8 responses across
  address/configuration/command/voltage/current/temperature registers. No
  evidence of conflicting same-address responders was observed; this is not
  a universal proof of single-device topology.
- STATUS_BYTE78h=0 establishes that the candidate reports supplying its output.
- 23h is a signed low8 word with6.25mV units. 21h is an unsigned low9 command
  with6.25mV units. E1h bit4 selects PMBus vs PWMVID; other E1 fields must
  be preserved. OPERATION[5:4] and three-level PWMVID45h bit5 affect selection.
- No password, EEPROM, protection, address, PAGE or frequency change was made.
  BUF_REG_UPD05h was researched but **never sent**. It also commits buffered
  frequency BDh, so it must not become a speculative activation fix.
- Exploratory fine-sense trim/PWM-endpoint/B4 tests did not establish a control
  recipe and were restored. Internal ADC readings cannot independently prove a
  physical sense-amplifier-trim response. No gain compensation is inferred.

## Working PMBus path at a low graphics clock

`probe_strix_mp2888_commit_no05.json` records a bounded experiment using the
adapter's enumerated405MHz floor. The clock was observed at405 throughout;
STATUS_BYTE78h remained0 and voltage sample ranges were0-2mV.

| Mode | Nominal21h command | Median READ_VOUT8Bh |
| --- | --- | --- |
| PWMVID baseline | inactive787.5mV | 676mV |
| PWMVID, command staged | inactive1100mV | 676mV |
| PMBus | 1100mV | 1066mV |
| PMBus | 1000mV | 968mV |
| PMBus | 900mV | 869mV |
| PMBus | 1100mV | 1066mV |
| PMBus | 1125mV | 1091mV |
| PMBus | 1100mV | 1066mV |
| PWMVID restored | inactive1100mV | 676mV |

All14 captured controller registers matched entry after restoring the original
inactive21h command. The owned frequency clamp and fans were restored. No05h
was needed. READ_VOUT differs from the nominal command by31-34mV here; this
is **not** a calibrated mapping to physical voltage and must not be compensated
with a board-specific constant.

`probe_strix_mp2888_coarse_pmbus.json` then kept21h at1000mV in PMBus mode:
23h offsets0/+25/+50/+100/0mV produced medians968/993/1018/1066/968mV.
Switching back to PWMVID returned676mV; all captured registers, clock and fan
state were restored. Coarse offset responds in this tested PMBus configuration.
A prior small-command-step test under a high V/F hold remained flat; its
operating-condition dependence is unresolved and is not evidence for an
undocumented activation command.

At a later moderate1500MHz graphics lock, the same1000mV command reported967mV
versus968mV at405MHz. An old research script then attempted23h through the new
production adapter, which now deliberately permits only21h/E1h writes. The
adapter refused that step before dispatch; the script's old23h cleanup call
also refused. A focused recovery confirmed23h was unchanged, restored PWMVID
(676mV), restored the inactive21h command, checked the complete entry context,
and released the owned405MHz clamp. The journal records this recovery; no
manual voltage or clock hold was left active.

## Production implementation and validation

The implemented path is explicit manual PMBus control, with a nominal21h request,
preserved coarse/fine configuration, bounded combined request, and controller
readback labelled as reported rather than physical voltage. Manual application
needs an owned, observed minimum graphics-clock clamp before voltage changes.
Auto/exit restores captured controller state before releasing that clamp.
Controller recovery cannot depend on unrelated GPU temperature/clock telemetry.
Saved legacy offsets cannot become absolute voltage. Manual PMBus control is
session-only until a complete profile/clamp replay contract exists.

`validate_strix_mp2888_production.json` records the production controller and UI
lifecycle methods against this adapter, with GUI rendering/persistence replaced
by journal hooks. The verifier passed900/925/900mV with reported870/891/870mV.
Apply1100/1125/1100mV produced1066/1091/1066mV. Manual1100mV remained1066mV
at an observed1500MHz graphics clock; the next Apply reacquired405MHz first.
Release restored the exact captured entry before releasing the clamp. Auto
selected PWMVID, and the harness also restored the inactive original command.
The complete final control matched entry; no NVML/VF lock remained and fans
were restored. All four production-source hashes were unchanged during the run.

The full software suite passes2028 tests. New MP/clamp/profile tests pass Ruff;
modified legacy files add no lint diagnostics relative to tag1.8.0. Independent
adversarial review found no remaining blocker after recovery/ownership fixes.

The user left before PMBus-path experiments. Independent meter validation of
this new path remains for their return; no post-departure physical readings
are invented. Desktop screenshot capture failed with `FrameArrived timed out`
and `window capture timed out`, so no visual GUI check is claimed. Nominal
requests in the working-path and production tests never exceeded1125mV.
