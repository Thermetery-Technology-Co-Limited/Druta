# The same GP106 on driver 516.94: same packet, different records

On 2026-11-02 the Gigabyte GTX 1060 6GB used throughout the 1.9.06 and 1.9.07
work was tested on **516.94**, same board, same VBIOS `86.06.4b.00.32`.
Detection failed with `0x2080A630` refused, and both the extended ceiling and
the current sliders were unavailable.

Fourth driver on this board, fourth distinct failure. Companion to the
[576.80](pascal-gp106-live-power-20261102.md),
[572.83](pascal-gp106-driver57283-20261102.md) and
[472.12](pascal-gp106-driver47212-20261102.md) reports.

## Command family and record layout are independent

This driver presents an A612 transport — command `2080A612` — at **3548/3480
bytes**, the exact packet geometry 472.12 presents under `20802612`. It then
answers the **A6xx** command ids while laying its policies out the compact
way that family uses.

So the same packet geometry means two different things depending on the
command that carried it, and the records are not the same either:

| | `20802612` 3548/3480 (472.12) | `2080A612` 3548/3480 (516.94) |
| --- | ---: | ---: |
| Commands | `2080_26xx` | **`2080_A6xx`** |
| Client INFO / CONTROL | 900 / 388 | 900 / 388 |
| Role INFO | 136 | **132** |
| Native INFO (record) | 5520 (132) | **5392 (128)** |
| Native CONTROL | 2124, `0x14` / `0x34` | 2124, `0x14` / `0x34` |
| Native STATUS (record) | 69148, `0x64` / `0x828` | **70684, `0x64` / `0x858`** |

`_CURRENT_LIMIT_LAYOUTS` is therefore keyed on the transport's **command as
well as its sizes**. Keying on size alone cannot represent these two.

The role-size rule holds again: 132 = 4 + 128.

## The size-refusal code is a property of the driver, not the family

The [472.12 report](pascal-gp106-driver47212-20261102.md) recorded RM `0x3A`
for a wrong size and suggested it belonged to the RM26 families. **That was
wrong, and this driver disproves it**: 516.94 returns `0x3A` on the *A612*
family, which 572.83 and 576.80 answer with `0x1F`.

Which code a driver uses is a property of that driver. Both are now treated
as the definite "wrong size" answer that selects the next candidate, which is
what detection needed here — the modern 2340-byte client INFO was refused with
`0x3A`, and 1.9.06's fallback only moved on for `0x1F`.

Sweeps accepted exactly one size per block, every other size returning `0x3A`:
client INFO 900 of 256..2600, role INFO 132 of 4..1024, native CONTROL 2124 of
512..8000, native INFO 5392 of 1024..12000, native STATUS 70684 of
4000..210000. Notably 69148 — the status size the 26xx transport of the same
packet geometry uses — is refused here.

## Record geometry

Native INFO base `0x3C` with a 128-byte record binds role 1 to policy 2. Two
other bases produce a unique match for the single bound definition and were
rejected because they decode the other nine occupied policies as zeros: a base
shifted by whole records always matches the one record you searched for.

The status base and stride were solved from live data as before. With the mask
at word 0 the driver populates the block; of every `(base, stride)` with base
0..2048 and stride up to 12000, exactly one makes all ten occupied policies'
status type bytes equal their info type bytes and keeps every effective value
inside its own bounds: `0x64` / `0x858`.

The decoded policy table is the one this board reports on every driver,
including core current at type `0x0B`, channel 11, 1000/86800/95000 mA.

### One thing that could not be measured

Only client row 0 is occupied on this adapter, and row 0 sits at the base for
any stride, so the **client INFO record stride cannot be determined here**. It
is taken as 28 from the matching 900-byte group. Confirming it needs an
adapter that occupies more than one client row.

## Reversible idle trials

Captured baseline 180 W; every trial restored it, watchdog armed.

| Trial | XOC | Result |
| --- | --- | --- |
| Power 190 W | no | exact readback, restored |
| Power 201 W | yes | exact readback, restored |
| Power 250 W | yes | exact readback, restored |
| Core current 86.8 → 86 A | — | accepted, effective limit verified |
| Core current 95.001 A | — | refused, no state change |
| Core current restore 86.8 A | — | effective limit verified |

Native effective power reads 185625 mW against a configured 180 W.

## Scope

Idle software observations on one adapter across four drivers. They do not
establish physical enforcement under load, behavior on other Pascal boards or
drivers, or any change in actual power draw. See the
[472.12 report](pascal-gp106-driver47212-20261102.md) for the one under-load
measurement taken on this board, which found core current — not board power —
to be the binding constraint.
