# Focused native port inventory — 2026-11-12

## Scope and evidence

Read-only functional comparison of released Python **1.9.1 (`fa6ee83`)** with native UI at **`d5034e82169a673d64198e6d9a54680877ad67bd`**, plus the root agent's stated in-flight routing changes. Python line references below refer to `git show fa6ee83:<path>` (the current Python working tree has changed). All native line references are pinned to `git show d5034e8:<path>`; they deliberately describe that baseline, with subsequent approved routing/helper changes called out separately. No build, app launch, GPU operation, production edit, commit, or push was performed.

Trace used: Python widget → callback → runtime/profile module, compared with native navigation → draw function → `Command` → worker/session → `core_client.cpp` execution/service → available C ABI. A missing draw function is distinguished from an absent native runtime service. Public low-level transport access alone does not constitute a port of a feature's semantic writer.

Status terms:

- **Binding**: native backend/service exists; add command/UI/session integration.
- **Partial**: visible workflow exists but an observable Python behavior is absent.
- **Backend**: no corresponding complete native semantic service/ABI was found; requires a bounded backend port before UI writes.
- **Parked/research**: implementation or capability exists but qualification/physical meaning remains unresolved. This is not an absent implementation or authorization to replay opaque state.

The accepted Focused design remains fluid and less verbose, with separate Rails/I2C tabs and gate flashes; the large V/F popup, visible points, WASD and Shift are intentional. Additional-memory domain 2 belongs in Advanced; NVVDD/MSVDD offsets belong in Rails; Crossbar/SYS/Video/LTC remain in Daily. The root agent has implemented those routing changes, so their pre-edit locations are **not backlog items**. Classic presentation parity is outside this report.

## Prioritized port checklist

### P1 — complete an existing interaction (working button already available)

- [ ] **V/F Ctrl+H initiates and releases the selected-point hold — Partial/Binding.** Python release binds H in `druta.py:8890`, `on_key_hold:9524` executes the toggle, and `vf_keys:11832` documents it. Native `curve_keyboard` (`ui_view.cpp:661–702`) handles Ctrl+Z/Y then returns whenever Ctrl is down. The only Ctrl+H dispatch (`:1504`) is inside `maintenance_needed()`, so it releases an existing hold but cannot initiate one. Reuse the existing hold button command (`:968–972`) and `core_client.cpp:723` hold preflight. Acceptance: focused popup Ctrl+H holds the selected fresh point, second press releases; locked/busy/stale/dirty/typing cases send no new hold; one press cannot both initiate and release; release remains available through ownership recovery.

- [ ] **Clarify local lock-diagnostics/status copy — Partial, small companion edit.** `ui_view.cpp:1055` says owned holds and recovery controls are not enabled "here yet", meaning Advanced. That local statement can confuse users because the popup hold button and global release already work. Clarify the local scope and optionally show ownership/status from `TuningState`; preserve uncertainty. Acceptance: active/unconfirmed/recovery-pending owned hold has consistent status in Advanced and popup; unreadable external locks are not described as unlocked.

### P1 — other high-value read-only bindings and explicit saved profiles

- [ ] **Monitor raw sensors, power split, utilization and reason lamps — Binding.** Python `druta.py:704–794` builds Monitor and `:692` defines bars; refresh is `druta.py:1800` (`refresh_monitor`). Native `ui_view.cpp:1084–1113` draws three histories plus a small sensor subset. `dc_telemetry` (`native/include/drutacore/drutacore.h:290–368`) already carries video/xbar, temperature sensors/delta, GPU/board percentages, GPU/FB/video/bus utilization, throttle/event/perf-decrease masks, PCIe link/errors, P-state, energy and lock fields. `core_client.cpp:929` loads telemetry; `session.cpp:22–46` preserves missing prior readings and stale masks. Add compact optional groups, not a new telemetry backend. Acceptance: alternate partial adapters, absent bits, zero-valued valid readings, transient missing fields and paused state render correctly; no unknown field appears as a measured zero; unrelated absent sensors do not remove useful groups.

- [ ] **Monitor all-clock-domain A/B table and measured-vs-reported clock context — Binding plus small read-only view model.** Python `druta.py:827–1014` (`build_domains`, `refresh_domains`) decodes the two arrays and per-adapter names/grades; `:1035` (`refresh_real_clocks`) adds measured qualification. Native telemetry already carries `priv_clocks[288]` and `DC_T_PRIV_CLOCKS` (`drutacore.h:295,330`), and `native/include/drutacore/clkdom.h:51–61` exposes `dc_gpu_clock_domains` / `dc_clock_domains_classify`. Focused Monitor has no domain binding (`ui_view.cpp:1084`). Add read-only normalized rows and freshness, then the table and qualified secondary clock readings. Acceptance: test alternate architectures/domain identities, doubled units, raw PCIe domain values, unidentified/unpopulated domains and transient failures. Never label B as universally measured or bake one board's domain mapping/grid into the view.

- [ ] **Manual V/F curve profile save/load — Partial/Binding.** Python full-profile capture/save/load (`druta.py:10658`, `:11109`, `:11289`; `profiles.py`) includes curve state. Native `core_client.cpp:699` explicitly says core curve, policy rows and rail limits are not saved, even though snapshot/apply/reset/undo are implemented (`:500–546`). Extend a versioned, target-bound profile schema and stage/preview curve before explicit application. Acceptance: reject changed geometry/divisor/identity and unsupported fields before writes; preserve unsaved curve draft; exact selected requests after apply; partial failure retains meaningful Undo; no startup/post-reset replay.

- [ ] **Manual rail-limit and individual policy profiles — Partial/Binding.** Python `ordinary_profile_contents` (`druta.py:10705–10737`) offers rail limits and coupled power/current scopes; `rail_limit_profiles.py` / `power_action_profiles.py` supply semantic capture/validation. Native has rail and policy actions (`core_client.cpp:402–459`, `execute_policy`) but the daily profile deliberately excludes them (`:699`). Add each scope separately using bindings/units and existing selected-field writers. Acceptance: round trip a subset on a different valid layout identity; absent unrelated rails do not erase supported entries; changed binding rejects writes; no broad opaque table replay; explicit action only.

- [ ] **Profile catalog, selected scope and combine UI — Partial, after scopes.** Python list/selection/combine (`druta.py:10797–11068`) exposes saved choices and composed scopes. Native opens one file dialog (`main.cpp:229–248`); native schemas and iCX preset dialog are distinct. First provide an honest included/omitted summary and selectable qualified scopes, then optional catalog/combine. Acceptance: unsupported Python profile scopes are explained precisely; composition preflights all entries and duplicate/conflicting scopes; loading a profile never silently imports startup behavior. Python `set_startup_profile:11459` is intentionally excluded from ordinary session-only tuning.

### P2 — expand existing native services without conflating them with new backend work

- [ ] **Clock lock min/max/lock-max and legacy P0/max fan — Binding/session ownership.** Python Clocks menu (`druta.py:11592–11823`, `apply_lock:7021`, `lock_p0_and_max_fan:6860`) exposes frequency holds independent of V/F voltage-point holds. Add a dedicated ownership-aware service/command rather than borrowing I2C's clamp ownership. Acceptance: current adapter range/capability discovery, mutual handover between owned lock types, exact request readback, explicit release and uncertain-state recovery; never release somebody else's lock.

- [ ] **Hard de-flatten with explicit hardware-mod acknowledgement — Binding.** Python `vf_hard_deflatten` (`druta.py:10335`) and `build_vf` expose this separate operation. Port pure planning and staged preview first, preserve explicit acknowledgement, reuse existing curve apply. Acceptance: unchanged unknown points/fields, out-of-envelope rejection, correct device-specific grid and full undo/redo; no hardware behavior claim from the software model.

- [ ] **Advanced read-only PERF policy diagnostics and arbitration — Binding / partial orchestration.** Python `registry_panel.py:378–410` builds diagnostics; callbacks `:1128`/`:1187` read arbitration/PERF. Bind PERF groups first; arbitration additionally needs explicit read orchestration around existing power layouts and decoder. Acceptance: bounded retry and per-group unsupported/transient states, current target binding, preservation of last good display, no writes or interpretation of unknown policy fields.

- [ ] **Timings profile save/load, multiple staged fields and captured restore — Partial/service extension.** Python `druta.py:12485–12505` exposes staged apply/clear/stock/profile actions, `tw_save_profile/tw_load_profile:12700–12775`, `timingprofiles.py:226–290` validates the profile. Acceptance: helper absent versus unavailable driver get distinct actionable text; timeout restores only owned hold; no unrelated tuning replay. ### P3 — genuine native semantic backend ports; keep unresolved research parked

- [ ] **Power-policy feedback/integral bounds — Backend.** Python `druta.py:2736` constructs `PowerIntegralPanel`; `power_integral_panel.py:123,183,189` invokes its live controller, and `power_integral_runtime.py:165–223` owns specialized read/selected SET/readback/restoration. Native policy limit setters do not implement these feedback fields: `backend.h:31` (`PowerPolicy`) exposes only scalar limit state and `Command` has no bounds operation. Port reader/decoder first, then only understood fields with exact selected readback; add scoped profiles later. Acceptance: varied policy identities, missing status, transient failures, unrelated byte preservation and restore after partial writes.

- [ ] **Live voltage gate, V/F monotonicity/smoothing, offset/request tables, REL bounds, constants and device delays — Backend.** Python `registry_panel.py:157–327` wires widgets into individual runtimes; callbacks `:539–1040`, `voltage_offsets_panel.py:73/141`, `voltage_requests_panel.py:133/174` trace to semantic readers/writers. These are different from native NVVDD/MSVDD offsets and rail limits. Native command/data model (`backend.h:25–31,87–118`) contains no equivalent gate/table/policy/bounds/constants/delay state or commands; public header/service inventory contains no corresponding complete native service. Increment separately per control: read-only inspection → validated selected-field request → restoration/Undo → manual scoped profile. Acceptance: current-adapter capability/layout checks, unit/identity validation, exact selected readback, bounded transient recovery and preservation of unknown fields. Unresolved meaning stays read-only/parked.

- [ ] **Live power-saving/PCIe controls — Backend.** `RegistryPanel.build` calls `build_live_power` (`registry_panel.py:105–110,329–376`), which constructs GR/individual power gating, GR idle threshold, adaptive power, engine/block/second-level clock gating, DIFR and PCIe speed panels. Example callback traces: `pcie_speed_panel.py:111` → `pcie_speed_live.py:94` read/controller path; `gr_gating_live_panel.py:114` → its controller. Neither `backend.h` nor native core's public feature headers expose those complete semantic controllers. Treat every family as an independent port; shared packet transport is not a substitute for the Python ownership/capability contracts. Acceptance: read-only first, alternate identities/partial capabilities and transient failures; selected understood field only; explicit session action, release/Undo, no startup/reset reapply.

- [ ] **Registry/VBIOS editor and relationship-weight override exception — Backend.** Python `registry_panel.py:121–155` builds read/preview/apply/restore; `refresh:1314`, `prepare:1608`, `apply:2041` call the registry override workflow; `power_weight_runtime.py:48,240` reads/annotates qualified relationship weights. Native clock-BIOS reader is not a registry editor; no native command/schema/service here implements override preview, write receipt, driver-refresh verification and restoration. Scope any new implementation first to the user's narrow weight exception, preserving other VBIOS/registry state. Acceptance: qualified current-adapter relationship binding, exact changed multiplier/retained INFO verification after explicit refresh, rollback/removal; explain persistence. Do not generalize that exception to ordinary tuning or port the rest of Python's persistent editor by implication.

## Remaining I2C polish, lower priority than missing features

Python supports cancellation and remembered discovery routes (`druta.py:4751`, `:4937`, `:4805`; `i2c_cache.py`). Native `i2c_view.cpp:233–336` offers scan, full scan and explicit route, but no cancel or persisted route selection UI; no matching cancel operation exists in `backend.h:87–92`. This is **Partial/session workflow**, not missing controller support. A saved route may only speed read-only discovery and must be re-probed for current identity/geometry before writes. Acceptance: cancel stops at bounded read boundaries, no partial scan becomes verification, a stale remembered route never authorizes a write. Never persist/replay controller requests on launch/reset.

## Suggested bounded implementation order

1. Ctrl+H activation + clearer local hold status, using existing action preflights; this is interaction parity, not a critical missing hold feature.
2. Monitor scalar/reason bindings, then classified clock domains/measured qualification.
3. One manual profile scope at a time: V/F → rails → policy rows; selected-scope UI after schemas.
4. General owned frequency lock and pure hard-de-flatten planning.
5. PERF read-only diagnostics and timing stage-only profiles; transaction expansion separately.
6. Only then select one understood Advanced backend family. Unresolved firmware/control research remains parked.

Each increment needs behavior-level tests for alternate identities, partial capabilities, transient reads and failure/restore behavior, plus focused visual verification where UI changes. Existing headless suites and reported local MP2888 qualification are useful baselines, not evidence that all other adapters/controllers are qualified. This audit establishes source parity gaps only; it makes no physical safety or universal hardware-response claims.
