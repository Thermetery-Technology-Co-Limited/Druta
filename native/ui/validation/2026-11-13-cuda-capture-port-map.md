# CUDA timing-capture fallback port map

Read-only audit, 2026-11-13. Python reference is pinned `fa6ee83`; native baseline is `5f6fb49` with the current integration working tree. No hardware, process launch, build, or source implementation was performed. This missing fallback remains part of the parity ledger; “optional CUDA dependency” does not mean optional implementation.

## Exact missing behavior

The release's **Read at P0** action first tries an owned legacy P0/VF hold; when controls are locked, NVAPI/curve support is absent, or acquisition cannot qualify, it falls back to an ordinary CUDA device-to-device copy workload and captures timings **while that workload is still running**. Already-qualified P0 captures bypass CUDA completely. CUDA induces whatever state the driver chooses; it does not force P0.

Native `capture_qualified_timings` supports only direct qualified P0 or a bounded wait under an existing/new hold. Failed acquisition returns immediately, no workload runs, and the view disables this action when controls are locked. Thus precisely the release cases that needed the fallback cannot use native capture. An existing CUDA warmup implementation is available, but is not connected to timing capture and cannot safely be called followed by a capture after it returns.

## Available dependencies and minimum API change

No CUDA toolkit, PTX/kernel compiler, cuBLAS, NVRTC, or new RM escape export is required. The workload is bandwidth copies through the CUDA **driver** DLL. `i2c_warmup.h:17–30` already defines an injectable narrow `I2cCudaApi`: init, lookup/readback BDF, context create/destroy/sync, free-memory query, allocation/free and DtoD copy. Its loader uses the absolute Windows system-directory `nvcuda.dll` and resolves actual symbols (`i2c_warmup.cpp:42–49`). Missing DLL/exports/capability must produce a specific unavailable reason, retaining manual/direct capture; no driver-version gate.

The minimum coherent refactor is a shared workload runner plus an unchanged I2C adapter:

1. Move/reuse the narrow CUDA API and lifetime implementation behind a neutral workload interface. Do not copy a second independently evolving loader. Keep existing I2C warmup behavior as an adapter that reads voltage while the shared runner is alive and stops before P0 verification.
2. Add `CudaWorkloadTarget{generation,slot,uuid,helper_token}` (or existing timing target plus bound identity), `CudaWorkloadOptions{startup_timeout,settle_timeout,max_duration,poll}`, and callbacks `bound()`, `cancelled()`, `sample()` and `on_settled()`. The callback returns a typed read-only timing snapshot/result, not a tuning callback. Check cancellation/binding/workload-alive/deadline immediately before and after it. No callback after expiry or cancellation. Failed/moving reads remain diagnostics, never permission to write timing fields.
3. Extend timing capture orchestration with method/result states: direct, existing hold, temporary hold, CUDA fallback, unavailable, cancelled, cleanup pending. A failed **unissued** hold may proceed to CUDA. An issued/uncertain hold must finish owned cleanup before considering workload; no CUDA warmup on top of an uncertain tuning request. Foreign/uncertain holders remain protected. Recheck direct qualification before starting CUDA, including after cleanup, to avoid lowering an already-qualified state.
4. Capture through the pinned selected helper while CUDA is demonstrably copying, then signal stop and join/confirm owned context teardown before returning success. Failure must carry captured diagnostics separately from accepted qualified snapshot. Context/cleanup errors and early workload expiry invalidate success even if a callback returned data.
5. Use current-adapter capabilities, actual state, offset and helper evidence for qualification. A successful memcpy or settled memory clock is not evidence of P0, timing-band equivalence, or physical gating. Do not change compute caps, force P-states through undocumented paths, change fan/power/offsets, or clear foreign tuning ownership to make the fallback work.

### P2 qualification boundary that must remain explicit

The release's lower P2 floor in `timings.py:837–852` is limited to codename strings GP102/TU102 with adjacent reported clocks≤200, justified there by measurements on those devices. Repository instructions prohibit turning developer measurements into a universal compatibility/physical-equivalence gate. Native currently uses the enumerated top and does not carry that lowered floor.

Port the workload and honest diagnostic P2 capture now without inventing a generation-wide lower floor. Preserve current exact band qualification when P2 reaches it. A below-current-floor P2 capture can remain visibly unqualified/raw; it must not gain timing-write/profile eligibility merely because the workload ran. Full released lower-P2-band equivalence needs authoritative layout evidence or current-adapter independently bound P0/P2 comparison evidence, with explicit scope and tests. This is a separate remaining semantic qualification dependency, not a reason to drop CUDA fallback. Do not use measured local clocks/offsets as constants.

## Bounded lifetime and Pause

The current native six-second **settle loop** is bounded (`timing_capture.cpp:35–39`), but the helper subprocess/driver calls have their own durations. `TimingCaptureCallbacks` has no cancellation callback. `Session::set_paused` (`session.cpp:487–503` in this working tree) clears pending telemetry requests and marks resume freshness; `main.cpp:consume_timing_auto` suppresses auto-capture when paused. It does not interrupt an already-running explicit timing action. Python's general `gpuload.induce` accepts cancellation, but this particular release UI call at `druta.py:13862` does not pass it. Therefore do not falsely claim existing Pause already cancels either capture worker.

Required native behavior should be explicit: no workload starts from recurring/auto-capture polling; only a user action starts it. Pause suppresses auto-capture and recurring observations as today. Add a capture-cancel token which Pause/close/selection invalidation can signal without waiting behind the worker queue; check it at bounded startup/settle/copy boundaries. Cleanup of already-owned resources remains allowed while paused, without resuming unrelated telemetry. After resume, no automatic workload restarts; fresh telemetry and a new explicit action are required.

A wall-clock deadline around a CUDA loop cannot preempt a blocking CUDA allocation/copy/sync/free/destroy call. Existing `i2c_warmup.cpp:141` uses unbounded `worker.join()`. Python `gpuload.py:414` joins with a timeout and daemon thread, which can leave the thread/context alive after return. Neither establishes a hard end-to-end bound under a stuck driver; do not inherit either while claiming bounded cleanup.

For a hard UI/session bound, host the CUDA runner in a dedicated exact-target child process with a bounded ready/ended/stop protocol and lifetime/job ownership. Keep the selected `nvtune` capture in the parent timing worker while the child reports an active workload; invalidate capture if child exits or deadline elapses. At timeout/cancel, stop then terminate only this owned workload child if necessary, retain diagnostics, and do not publish success until process termination is observed. OS/driver completion itself cannot be guaranteed under a hung kernel; report that limitation rather than silently detaching a thread. Existing native hidden child/process/quoting infrastructure can be reused; no child launch may default to another GPU or carry startup tuning arguments.

## Acceptance and tests needed

- Already-qualified P0/direct capture creates zero CUDA contexts and acquires zero holds. Existing confirmed owned hold is neither reacquired nor released. Temporary capture-owned legacy/VF request is always released; failed release remains visible for explicit recovery.
- Locked controls, absent NVAPI/curve and qualified unissued hold failures can reach workload fallback without any tuning SET. Issued uncertain hold failure cannot start CUDA before owned cleanup. Partial voltage capability does not disable timing workload.
- Injected CUDA tests: alternate device order/BDF, normalized BDF formats, wrong BDF, empty/malformed slot, UUID appearance/change and generation/helper changes; no ordinal fallback, no default GPU, zero copy/context on mismatch.
- Missing DLL/each required export; insufficient free memory; min/max/rounding bounds from current free VRAM; first/second allocation failure; init/context/copy/sync/cleanup failures. All frees/destroy on the creator worker and only for owned nonzero resources.
- Successful capture callback observes live copies and bound helper; no capture-after-stop ordering; workload ends during startup/settle/before callback/during callback; all invalidate appropriately. Settling timeout, hard deadline and partial diagnostics are explicit.
- P0 versus P2 actual labels; offset-normalized band checks before/after; moving memory/pstate/helper/identity; unrelated valid read retained. P2 below current qualified floor never silently becomes a timing-write/profile authority. No board/driver allowlist added.
- Cancellation before start performs zero CUDA calls; during startup/settling prevents callback; after callback starts waits for/read-only capture completion then owned teardown; Pause and close signal outside the queue. No automatic startup/resume/reset workload or tuning replay.
- Deterministic blocked-call child tests prove parent deadline and termination handling, no lingering owned process/context claims, no UI/session hang hidden by an unbounded thread join. Reboot/device-loss/child-error reports remain honest.
- View supports direct/hold/workload statuses and actual landing reason; one explicit read-only fallback can be selected while tuning is locked, holds still require unlock, and cancelling/recovery remains accessible. Auto-capture continues consuming normal polled observations only.

Reuse/extend `native/ui/tests/i2c_warmup_test.cpp`, `timing_capture_test.cpp`, `timing_capture_service_test.cpp`, `timing_capture_client_test.cpp`, `timing_capture_session_test.cpp`, and existing selected-helper transport tests. Source behavior tests are `tests/test_gpuload.py` and `tests/test_gpuload_cancellation.py` (startup/cancellation/callback lifetime/deadline cases). No tests were run by this audit.

Remaining scope: CUDA workload implementation exists for I2C voltage warmup; **timing capture fallback, timing-specific workload cancellation/progress, hard-bounded process ownership, and faithful P2 diagnostics/qualification are not implemented by this report**.
