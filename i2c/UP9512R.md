# uP9512R load-state voltage offsets

Druta implements the uPI uP9512R's five positive offset fields through a built-in
[controller adapter](../src/druta/controllers/up9512r.py). **Offset (all load
states)** stages one common request for LCS0 through LCS4 in 10 mV steps.
The separate readback describes all five programmed values and whether offsets
are enabled. Mixed fields and unavailable reads are shown explicitly; the
staged slider is not evidence of an applied common offset.

On the tested RTX 4080 SUPER, discovery and reads worked on both tested
drivers, but the first verification write failed. Apply therefore remains
unverified on that board; see [the hardware results below](#validation-status).

Checking **I2C rail** reveals the manual discovery controls without accessing
the bus. Select **uPI uP9512R**, then **Connect / Scan**. A compatible saved
route is checked first; otherwise the selected controller's routes are scanned.
**Full scan** ignores the saved route and controller filter. Launch, checking
the box and switching GPUs do not start discovery. Multiple candidates require
an explicit selection, or an exact saved-profile identity match.

After successful per-session **Verify**, **Apply** sets all five offsets and
enables them. **Reset** zeros all five and clears the enable bit. Reset uses
the same selected connection and requires prior verification or a verification
write attempt eligible for recovery. It does not test an untouched controller.
The adapter never writes the SMBus lock, so an already locked controller remains
readable but cannot be adjusted by Druta.

## Register evidence

The source is uPI's **uP9512R-DS-F0000, November 2018**, Table 8, printed pages
17–23, with the byte transaction format on page 16. The manufacturer's
[product page](https://www.upi-semi.com/upisemi/products/ic/dc-dc-controller/multiple-phase-buck-controller/up9512r/)
identifies the part. The manufacturer-authored
[datasheet copy hosted by Oneyac](https://uploadcdn.oneyac.com/upload/document/1754981236304_9415.pdf)
used for these fields has SHA256
`681ac5e3e3a76f598ea6fcba06fd80b34a07830b3ddfad6349f11172c7b7b1b2`.

| Register | Datasheet meaning | Druta behavior |
|---|---|---|
| `0x27`, `0x28` | Read-only vendor/device IDs `0x00`, `0x2B`; p. 23 | Read both twice to identify the controller; recheck during use |
| `0x0A[7:4]`, `0x0A[3:0]` | IICV0 and IICV1, LCS0/LCS1 offsets; p. 17 | Positive nibble values, 0–150 mV in 10 mV steps |
| `0x0B[7:4]`, `0x0B[3:0]` | IICV2 and IICV3, LCS2/LCS3 offsets; p. 18 | Same encoding |
| `0x0C[7:4]` | IICV4, LCS4 offset; p. 18 | Same encoding; preserve the low nibble |
| `0x2A[6]` | Output-offset enable; p. 21 | Change only this bit; preserve the other seven bits |
| `0x2A[7,1:0]` | Internal-test fields required to be zero; p. 21 | Refuse writes if any is nonzero |
| `0x2C` | IMON input ADC, 10 mV per count; p. 21 | Read-only **IMON**, in mV; no conversion to amps |
| `0x2D` | Output-feedback voltage report, 10 mV per count; p. 21 | Read-only **FB**, in mV |
| `0x39` | SMBus security lock; p. 22 | Read only; accept writes only when its value is already `0x94` |

The datasheet describes an unlock/relock sequence that then requires a VCC
power-on reset to reset the lock. Druta does not issue either transition:
`0x39` is excluded from its write-register set. Only `0x0A`, `0x0B`, `0x0C`
and `0x2A` may be written. Phase count, switching frequency, load line,
protection thresholds and protection enable controls are outside this adapter.

## Discovery, target binding and units

Discovery probes NVAPI ports 0–7 and seven-bit unicast addresses `0x08`–`0x77`,
trying `0x25` first. This search order is not a fixed board route or a claim
that every address is a documented strap. Controller IDs and the understood
byte-register transport decide whether a candidate is returned. There is no
GPU model, board/subsystem, VBIOS or driver-version allowlist.

The instance is bound to the selected GPU handle and identity plus its actual
port/address. It checks the understood 64-byte NVAPI I2C V3 packet layout,
export availability, one-byte response size and changed output-buffer sentinel.
Repeated identity/control reads reject incomplete or changing captures. A
matching controller does not establish which physical rail it drives; discovery
labels that rail unassigned.

FB and IMON are controller-reported input voltages with 10 mV quantization.
They are not a meter calibration of this board's rail or current. The adapter
does not derive amperes from IMON, infer a fixed board gain, identify the active
load-current state, or use GPU VID as a substitute for feedback measurement.

## Request guards and verification

Normal mode permits offsets from **0 to +50 mV**; **XOC** permits the complete
documented **0 to +150 mV** range. Both use exact 10 mV hardware steps. These
are software request policies, not board-rated operating recommendations.

An ordinary request requires readable FB between 300 mV and the software
ceiling: **1200 mV normally**, or **2000 mV in XOC**. Because the active LCS is
unknown, the guard checks the largest effective increase among all five fields
against the same ceiling. It also checks FB after dispatch. These arithmetic
guards do not establish a calibrated 1:1 physical voltage response or a safe
maximum for an attached GPU. Reset/recovery can release offsets outside the
normal envelope; identity, lock and preservation checks still apply.

**Verify performs real writes.** It requires a readable, held P0 operating
point and captures the complete entry control bytes. A bounded +10/+20/+30 mV
staircase adds the same increment to each effective entry offset, using only
rungs that fit the current software envelope and feedback ceiling. For disabled
entry offsets, the effective starting offsets are zero; the stored entry fields
are still retained for restoration.

The verifier samples feedback before and after a rung, requiring a positive
response of at least one 10 mV ADC count and larger than observed variation.
It checks that P0, core/memory clocks, controller identity, control bytes and
XOC mode remain consistent. It stops at a response, refusal or cancellation,
then restores and independently reads back the exact original four control
bytes, including the five offsets, enable state and preserved bits. A pass
also requires the feedback to return toward its baseline with a downward
response above the observed variation.

A pass establishes a feedback response at that sampled operating point. It
does not verify every load state, sustained-load stability, calibrated gain or
board safety. Missing telemetry, movement indistinguishable from ADC resolution
or noise, and insufficient headroom leave verification inconclusive. Failed
restoration remains an explicit uncertain-state failure, not a successful pass.

## Profiles and transaction recovery

Tuning profiles use format `i2c.multi_state_offset` and save the compound
`up9512r-offset-v1` control: all five `offsets_mv` values plus `enabled`.
They can therefore preserve mixed states that the common slider does not edit
individually. The controller route and recipe identity must match on replay,
and the normal I2C opt-in and verification workflow still applies.

Each transaction captures the current complete control bytes. Changing fields
is followed by exact full-byte readback, preserving `0x0C[3:0]` and every
unrelated `0x2A` bit. Apply/Reset also compare their captured compound state
before dispatch, so another writer's intervening change causes refusal. A
partial or uncertain write attempts exact rollback only while the original
target and preserved bits still match; a failed rollback is reported explicitly.
No NVM commit, lock change or protection-disable operation is implemented.

## Validation status

The implementation has mocked transport, profile and UI regression coverage
for alternate routes/adapter identities, locked and unreadable controllers,
mixed states, preserved bits, failed writes and restoration. Those tests
validate the software contract, not successful physical adjustment.

The 2026-10-07 hardware checks covered one user-described Manli RTX 4080 SUPER
on NVIDIA **581.42 and 617.42**. Production discovery with only uP9512R selected
completed **896/896** route probes on each driver. Each sweep found one
candidate, at NVAPI port **2**, seven-bit address **0x25**, with vendor/device
IDs **0x00/0x2B**. The entry bytes at `0x0A/0x0B/0x0C/0x2A` were
`00/00/00/20`: all five offsets zero and disabled. The read-only SMBus lock
was `0x94`. Idle FB was 930-940 mV and IMON was 110 mV; these are quantized
controller ADC readings, not externally calibrated rail voltage or current.

Production **Verify** reached its first +10 mV rung at a held P0 operating
point on both drivers, then the first byte write, `0x0A = 0x11`, returned
**NVAPI status -1**. The returned byte count was 1 and both extra 32-bit words
were zero. Verification did not pass or establish a voltage response. All
four entry control bytes, the SMBus lock value and the temporary GPU holds
were confirmed restored. On 617.42, a separate explicit 100 kHz write of the
existing value `0x0A = 0x00` also returned -1 and left all four bytes unchanged.
These results do not identify why writes failed.

An independent diagnostic used the documented NVIDIA RM SMBus-byte operation
(`0x402C0105`, `SMBUS_BYTE_RW`) at 100 kHz, through the native I2C object created
by that process's NVAPI initialization and matched to the selected GPU. On
**both drivers**, repeated ID reads and all control/lock reads succeeded, but
the same-value write `0x0A = 0x00` returned **`0x16`
(`NV_ERR_ILLEGAL_ACTION`)**. Independent NVAPI readback confirmed the four
control bytes and lock remained unchanged. This narrows the observed error;
it does not establish the internal reason for refusal. The experimental RM
transport is not a production fallback.

An earlier 617.42 attempt at a loaded point reporting GPU VID 1195 mV was
refused by the controller FB ceiling guard before any write; the later attempt
used a 1000 mV GPU hold. GPU VID and controller FB are separate readings.
Neither result establishes a board-specific safe ceiling.

**Common Apply, profile replay and Reset were not exercised on hardware:**
verification did not succeed. They have mocked coverage only. The final
hardware-free suite passed **1649 tests**, including renderer checks. These
results are scoped to the tested board, drivers and operating points; controller
identification does not imply that writes will work on another board. See
[the Ada validation record](../ADA-VALIDATION.md#up9512r-i2c-discovery-and-verification)
for the driver-switch incident and final restoration scope.
