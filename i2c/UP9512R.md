# uP9512R load-state voltage offsets

Druta implements the uPI uP9512R's five positive offset fields through a built-in
[controller adapter](../src/druta/controllers/up9512r.py). **Offset (all load
states)** stages one common request for LCS0 through LCS4 in 10 mV steps.
The separate readback describes all five programmed values and whether offsets
are enabled. Mixed fields and unavailable reads are shown explicitly; the
staged slider is not evidence of an applied common offset.

On the tested RTX 4080 SUPER, discovery and reads worked on both tested
drivers, but the first verification write failed. Apply therefore remains
unverified on that board; see [the hardware results below](#validation-status).

A later private [changed-byte test](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-I2C-DISABLED-OFFSET-WITNESS.md)
proved reversible `0A: 00 -> 01 -> 00` register storage through a combined-prefix
route on both 617.42 and 581.42. Separate NVAPI reads witnessed the change and
restoration; `2A=20` and all other sampled registers stayed unchanged. Offsets
were disabled throughout the sampled states. This establishes storage writing
on this card, while enabled-offset voltage response and a production fallback
remain unverified. Apply, Verify and the packaged EXE are unchanged. No new
password, lock-register write or BIOS modification was needed for that test.

A subsequent private [combined prefix/read experiment](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-I2C-COMBINED-PREFIX.md)
was accepted on both 581.42 and 617.42: the request carries fixed `0A 00`
inline bytes before a one-byte read. NT/RM status was zero and independent
seven-register state remained exact. This establishes request acceptance,
not same-value write commitment; the controller's behavior at that repeated
START is undocumented. Apply, Verify and packaged application behavior are
unchanged. Both drivers were tested, 617.42 and exact controller state restored,
and the verified EXE reopened. No lock/enable register was written.

A later [live PMU request comparison](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-I2C-COMBINED-REQUEST-CAPTURE.md)
captured the exact prefix at the I2C read-builder CALL on both drivers.
Ordinary reads used configuration `0x2C2F`; the combined request used
`0x274F`, changing index length, software selection and speed code. This
confirms the request fields supplied to the PMU sender, not physical bus
frequency or controller write commitment. The production verification
requirement remains unchanged.

Checking **I2C rail** reveals the manual discovery controls without accessing
the bus. Select **uPI uP9512R**, then **Connect / Scan**. A compatible saved
route is checked first; otherwise the selected controller's routes are scanned.
**Full scan** ignores the saved route and controller filter. Launch, checking
the box and switching GPUs do not start discovery. Multiple candidates require
an explicit selection, or an exact saved-profile identity match.

After successful per-session **Verify**, **Apply** sets all five offsets and
enables them. **Reset** zeros all five and clears the enable bit. Reset uses
the same selected connection and requires prior verification or a verification
write attempt eligible for recovery. It does not test an untouched controller.
The adapter never writes the SMBus lock, so an already locked controller remains
readable but cannot be adjusted by Druta.

## Register evidence

The source is uPI's **uP9512R-DS-F0000, November 2018**, Table 8, printed pages
17–23, with the byte transaction format on page 16. The manufacturer's
[product page](https://www.upi-semi.com/upisemi/products/ic/dc-dc-controller/multiple-phase-buck-controller/up9512r/)
identifies the part. The manufacturer-authored
[datasheet copy hosted by Oneyac](https://uploadcdn.oneyac.com/upload/document/1754981236304_9415.pdf)
used for these fields has SHA256
`681ac5e3e3a76f598ea6fcba06fd80b34a07830b3ddfad6349f11172c7b7b1b2`.

| Register | Datasheet meaning | Druta behavior |
|---|---|---|
| `0x27`, `0x28` | Read-only vendor/device IDs `0x00`, `0x2B`; p. 23 | Read both twice to identify the controller; recheck during use |
| `0x0A[7:4]`, `0x0A[3:0]` | IICV0 and IICV1, LCS0/LCS1 offsets; p. 17 | Positive nibble values, 0–150 mV in 10 mV steps |
| `0x0B[7:4]`, `0x0B[3:0]` | IICV2 and IICV3, LCS2/LCS3 offsets; p. 18 | Same encoding |
| `0x0C[7:4]` | IICV4, LCS4 offset; p. 18 | Same encoding; preserve the low nibble |
| `0x2A[6]` | Output-offset enable; p. 21 | Change only this bit; preserve the other seven bits |
| `0x2A[7,1:0]` | Internal-test fields required to be zero; p. 21 | Refuse writes if any is nonzero |
| `0x2C` | IMON input ADC, 10 mV per count; p. 21 | Read-only **IMON**, in mV; no conversion to amps |
| `0x2D` | Output-feedback voltage report, 10 mV per count; p. 21 | Read-only **FB**, in mV |
| `0x39` | SMBus security lock; p. 22 | Read only; accept writes only when its value is already `0x94` |

The datasheet describes an unlock/relock sequence that then requires a VCC
power-on reset to reset the lock. Druta does not issue either transition:
`0x39` is excluded from its write-register set. Only `0x0A`, `0x0B`, `0x0C`
and `0x2A` may be written. Phase count, switching frequency, load line,
protection thresholds and protection enable controls are outside this adapter.

## EVC terminology and the three separate controls

Elmor's [uP9512 notes](https://elmorlabs.com/forum/topic/asus-rog-strix-rtx-3090/)
describe SMBus unlocking, external bus locking and voltage-command enable as
separate steps. These concepts therefore apply beyond the MP2888A, although an
EVC recipe for another board does not establish a working route on this board.

- **SMBus Lock:** the controller key at `0x39`, described above. The tested
  controller repeatedly reads `0x94`; no lock-register write was performed.
- **Lock bus:** EVC's bus-management function. Its
  [firmware notes](https://www.elmorlabs.com/forum/topic/evc2-beta-firmware/)
  describe preventing other bus transactions, with I2C clock options of
  100 kHz and 400 kHz. They do not specify the electrical locking sequence.
  A driver-local mutex does not reproduce control over other bus masters.
- **Voltage-command enable:** the uP9512R datasheet's corresponding output
  offset control is `0x2A[6]`. Druta already changes this bit, setting the
  offset fields before enabling them and preserving the other seven bits.
  The captured `0x2A=0x20` means offsets are disabled; setting only bit 6
  would produce `0x60`. This is an encoding example, not a completed write.
  The exact EVC UI-label mapping has not been checked against its XML profile.

Our first offset-register write failed before the enable step. The datasheet
does not identify bit 6 as permission to write the offset registers, and there
is no evidence that enabling it would resolve RM `0x16`. Phase-control fields
remain preserved; changing the regulator's operating mode is a separate
experiment, not an inferred unlock. The separate BAR0 diagnostic did not
establish control of SCL or replicate EVC's bus lock.

## Related RTX 4080 schematic: electrical route, not an unlock

The user-supplied Gigabyte `GV-N4080GAMING OC-16GD`, revision 1.01,
2022-09-29 schematic has 72 pages and SHA256
`c17ee9b513a4d4405b05471963f7020869cd156f075bc44cc5085d8057be7734`.
It describes a related RTX 4080 board, not verified component population or
continuity on the user-described Manli RTX 4080 SUPER. The following names
and reference designators apply only to that schematic.

- Page 26 routes GPU I2C-C through R20126 (SDA) and R20127 (SCL), both
  33.2 ohms. R20125 (SDA) and R20124 (SCL), both 2.21 kilohms, pull the
  controller-side bus up to `1V8_MISC`.
- Page 42 identifies U812 as `uP9512RQGJ/VQFN5x5-40L/S` on NVVDD. SDA
  reaches pin 34 through R363, and SCL reaches pin 35 through R348; both
  links are zero ohms. No active bus switch or level shifter is shown in
  this route. TP501 is SDA, TP503 is SCL, and TP502 is ground. The `0x4A`
  address annotation is consistent with the observed seven-bit `0x25`
  route. This corroborates a hypothesis, not physical rail assignment on
  the tested board.
- Page 37's Q714A/B and optional R785/R786 links instead form a 1.8-to-3.3 V
  I2C branch for the FBVDD MPS controller option. The sheet labels the
  branch `RESERVE I2C FOR MPS OVR3I+` and lists uP9529/MP2988 alternatives.
  Its combined `VID/SDA` and `REFADJ/SCL` labels must not be applied to the
  uP9512R's separate SDA/SCL and PWMVID pins. Parts marked `/X` and the
  co-layout alternatives require a population check before assuming continuity.
- Page 63 adds an OVR-M Gen2 prefilter option on I2C-C and explicitly notes
  1.8 V signaling support. Its stated eight-bit addresses `88/8A/8C/8E`
  correspond to seven-bit `44/45/46/47`. This is a shared-bus branch, not
  an identified bridge or permission gate in series with U812.

The nearby Q13A/B network on page 42 operates on the NVVDD enable circuit;
Q703A/B on page 37 operates on the FBVDD selection circuit. Neither is shown
as an enable for the Q714 I2C level shifter. Changing these controls is not
an evidence-backed SMBus unlock. The uP9512R datasheet also samples SCL at
power-on reset to select SMBus versus hardware programming. Existing repeated
register reads support an active SMBus interface, not a need to alter this strap.

The schematic identifies useful electrical comparison points and distinguishes
the voltage domains. It supplies no new controller password, firmware policy
override or accepted write. A passive capture on the actual board would be
needed to distinguish a refused request with no bus traffic from an emitted
transaction that receives a NACK or fails later. The previous software traces
did not capture those physical waveforms. Production write gating is unchanged.

## Discovery, target binding and units

Discovery probes NVAPI ports 0–7 and seven-bit unicast addresses `0x08`–`0x77`,
trying `0x25` first. This search order is not a fixed board route or a claim
that every address is a documented strap. Controller IDs and the understood
byte-register transport decide whether a candidate is returned. There is no
GPU model, board/subsystem, VBIOS or driver-version allowlist.

The instance is bound to the selected GPU handle and identity plus its actual
port/address. It checks the understood 64-byte NVAPI I2C V3 packet layout,
export availability, one-byte response size and changed output-buffer sentinel.
Repeated identity/control reads reject incomplete or changing captures. A
matching controller does not establish which physical rail it drives; discovery
labels that rail unassigned.

FB and IMON are controller-reported input voltages with 10 mV quantization.
They are not a meter calibration of this board's rail or current. The adapter
does not derive amperes from IMON, infer a fixed board gain, identify the active
load-current state, or use GPU VID as a substitute for feedback measurement.

## Request guards and verification

Normal mode permits offsets from **0 to +50 mV**; **XOC** permits the complete
documented **0 to +150 mV** range. Both use exact 10 mV hardware steps. These
are software request policies, not board-rated operating recommendations.

An ordinary request requires readable FB between 300 mV and the software
ceiling: **1200 mV normally**, or **2000 mV in XOC**. Because the active LCS is
unknown, the guard checks the largest effective increase among all five fields
against the same ceiling. It also checks FB after dispatch. These arithmetic
guards do not establish a calibrated 1:1 physical voltage response or a safe
maximum for an attached GPU. Reset/recovery can release offsets outside the
normal envelope; identity, lock and preservation checks still apply.

**Verify performs real writes.** It requires a readable, held P0 operating
point and captures the complete entry control bytes. A bounded +10/+20/+30 mV
staircase adds the same increment to each effective entry offset, using only
rungs that fit the current software envelope and feedback ceiling. For disabled
entry offsets, the effective starting offsets are zero; the stored entry fields
are still retained for restoration.

The verifier samples feedback before and after a rung, requiring a positive
response of at least one 10 mV ADC count and larger than observed variation.
It checks that P0, core/memory clocks, controller identity, control bytes and
XOC mode remain consistent. It stops at a response, refusal or cancellation,
then restores and independently reads back the exact original four control
bytes, including the five offsets, enable state and preserved bits. A pass
also requires the feedback to return toward its baseline with a downward
response above the observed variation.

A pass establishes a feedback response at that sampled operating point. It
does not verify every load state, sustained-load stability, calibrated gain or
board safety. Missing telemetry, movement indistinguishable from ADC resolution
or noise, and insufficient headroom leave verification inconclusive. Failed
restoration remains an explicit uncertain-state failure, not a successful pass.

## Profiles and transaction recovery

Tuning profiles use format `i2c.multi_state_offset` and save the compound
`up9512r-offset-v1` control: all five `offsets_mv` values plus `enabled`.
They can therefore preserve mixed states that the common slider does not edit
individually. The controller route and recipe identity must match on replay,
and the normal I2C opt-in and verification workflow still applies.

Each transaction captures the current complete control bytes. Changing fields
is followed by exact full-byte readback, preserving `0x0C[3:0]` and every
unrelated `0x2A` bit. Apply/Reset also compare their captured compound state
before dispatch, so another writer's intervening change causes refusal. A
partial or uncertain write attempts exact rollback only while the original
target and preserved bits still match; a failed rollback is reported explicitly.
No NVM commit, lock change or protection-disable operation is implemented.

## Validation status

The implementation has mocked transport, profile and UI regression coverage
for alternate routes/adapter identities, locked and unreadable controllers,
mixed states, preserved bits, failed writes and restoration. Those tests
validate the software contract, not successful physical adjustment.

The 2026-10-07 hardware checks covered one user-described Manli RTX 4080 SUPER
on NVIDIA **581.42 and 617.42**. Production discovery with only uP9512R selected
completed **896/896** route probes on each driver. Each sweep found one
candidate, at NVAPI port **2**, seven-bit address **0x25**, with vendor/device
IDs **0x00/0x2B**. The entry bytes at `0x0A/0x0B/0x0C/0x2A` were
`00/00/00/20`: all five offsets zero and disabled. Register `0x39` was read as
`0x94`; it was not written. Idle FB was 930-940 mV and IMON was 110 mV; these are quantized
controller ADC readings, not externally calibrated rail voltage or current.

Production **Verify** reached its first +10 mV rung at a held P0 operating
point on both drivers, then the first byte write, `0x0A = 0x11`, returned
**NVAPI status -1**. The returned byte count was 1 and both extra 32-bit words
were zero. Verification did not pass or establish a voltage response. All
four entry control bytes, the SMBus lock value and the temporary GPU holds
were confirmed restored. On 617.42, a separate explicit 100 kHz write of the
existing value `0x0A = 0x00` also returned -1 and left all four bytes unchanged.
These results do not identify why writes failed.

An independent diagnostic used the documented NVIDIA RM SMBus-byte operation
(`0x402C0105`, `SMBUS_BYTE_RW`) at 100 kHz, through the native I2C object created
by that process's NVAPI initialization and matched to the selected GPU. On
**both drivers**, repeated ID reads and all control/lock reads succeeded, but
the same-value write `0x0A = 0x00` returned **`0x16`
(`NV_ERR_ILLEGAL_ACTION`)**. Independent NVAPI readback confirmed the four
control bytes and lock remained unchanged. This narrows the observed error;
it does not establish the internal reason for refusal. The experimental RM
transport is not a production fallback.

On 2026-10-08 an explicitly approved, separate `drutadrv` BAR0 experiment was
tested on both **581.42 and 617.42**. A live VBIOS read resolved logical port 2
to physical controller 2 with no DPAUX sharing. At the historical line register
`BAR0 + 0xD054`, the probe attempted `0x07` (software mode with released pins)
but read back `0x33` (hardware mode with high line inputs under that layout).
It stopped after that single MMIO write, before any I2C bytes or uP9512R data
write. Independent BAR0/NVAPI checks found the original line state, controls
`00/00/00/20`, and lock `94`. A later installed-driver audit confirms the
register address and initial `07` command, but its callbacks do not require
bit 2 to read back as one. The observed mismatch therefore does not establish
a BIOS lock, a write restriction, or the bit's Ada readback semantics. It establishes no
successful BAR0 write transport or voltage response. The research driver is
not bundled with Druta; the existing verification gate remains in effect.
The bounded experiment and evidence are available in
[the separate driver research draft](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/pull/2).

A subsequent 617.42 SMBus lock investigation obtained three matching sets of
ID, control and lock reads through both NVAPI and RM `SMBUS_BYTE_RW` (42 RM
byte reads using two output sentinels). Register `0x39` remained `0x94`, the
datasheet's unlocked value. No unlock/relock or controller data write was sent.
The saved VBIOS I2C device table at `0x5B81` contains one active entry at
`0x5B86`, raw `47 4A 00 00`, matching RM's port-2/address-0x25 device. Its
write-access and read-access privilege fields are both zero. NVIDIA's
[DCB specification](https://nvidia.github.io/open-gpu-doc/DCB/DCB-4.x-Specification.html#i2c-device-table)
reserves the meanings of all privilege values; zero does not prove unrestricted
access. Header flag bit 0 disables external-device probing, not writes.

A separate documented `NV2080` privileged-read diagnostic returned RM success
but left both alternating output sentinels untouched, with and without the
privilege flag. It established neither valid device data nor a usable unlock
path. A missing controller key looks less likely: the datasheet documents
`39=94` to unlock and `39=87` to lock, with a 5VCC power cycle required to unlock
again after an unlock-then-lock transition. No further password is documented.
Reading `94` does not prove the internal lock latch or complete write path will
accept a request. GPU-side policy, ownership and line-control questions remain unresolved.
No BIOS modification, lock write or production transport fallback was added.

A further 2026-10-08 policy investigation tested the NVAPI Ex privilege flag
and direct RM privilege flags on both drivers. Reads remained valid; unchanged
`0A=00` writes still returned NVAPI `-1` and RM `0x16`. Selecting NVIDIA's CPU
software I2C route made known reads fail, so the guard sent no data write.
Selecting PMU software I2C preserved reads but still rejected the unchanged
byte with `0x16` on both drivers. The six data-write requests across this round
did not establish any physical write or voltage response. Each temporary
transport setting was removed, the device restarted, and independent RM/NVAPI
reads confirmed IDs `00/2B`, lock `94`, and controls `00/00/00/20`.

Static Windows-kernel analysis distinguishes the inspected host privilege
gate's `0x1F` failure from the measured `0x16`. It also finds a PMU completion
translation from Falcon `0x03` (`FLCN_ERR_ILLEGAL_OPERATION`) to RM `0x16`.
The firmware response itself was not captured, and lower host RPC post/wait
errors can propagate, so this does not yet locate the live rejection predicate.
Subsequent bounded reviews on both binaries found that the shared read/write
ownership paths' normal return values cannot produce `0x16`. Lower queue-path
exclusions on 617.42 remain conditional on unobserved runtime bindings and a
PMU memory-copy selector; no raw response byte had been captured at that stage.
See the [driver research record](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/I2C-POLICY.md)
for hashes, RVAs, the transport matrix and confidence limits. No additional
production workaround or write-capability claim follows from these results.

A separate fixed SCL diagnostic subsequently wrote `07`, then `06`, at the
corroborated line register on each driver. Both returned `33`, with no
SCL-low observation. Its output guard stopped before any intended address or
data bytes, with cleanup explicitly unconfirmed. The helper unloaded and a
manual display-device restart preceded independent reads matching the original
controller state. CPU-software identity reads also returned `FFFF` while
same-context cached port flags remained `11` before and after, so persistent
cached invalidity does not explain that failure. These results narrow the
investigation but establish neither an unlock nor a usable CPU write path.
Both overrides were removed and 617.42 was restored. The separate
[line-research record](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-LINE-PROBE.md)
contains the exact cleanup and interpretation limits.

Later live ETW captures positively identify both drivers' CPU read failures at
the SCL-high guard. Normal same-value writes instead reach the PMU send routine,
which returns `16` to its caller. That ETW round did not capture the raw response or exact refusal rule;
the lack of a lower-post error record supports only a
conditional response-translation inference. One further unchanged `0A=00`
request per driver was rejected, with independent exact state readback. The
transport settings were restored and 617.42 plus the verified EXE reopened.
See the [return-site analysis](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-I2C-ETW.md).
No additional unlock or working write support is claimed.

A later passive host-statistics query (`0x20803126`, a private binary-derived
interface) returned RM `0x56` with all 120 parameter bytes untouched on both
drivers. Each attempt stopped after its first rejected query; no counters,
raw response status or live eligibility flag were obtained. This round made
no controller-data write or direct research MMIO request. Both driver switches
completed and independent seven-register readback remained exact, with 617.42
and the verified EXE restored. The
[completion-diagnostics record](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-PMU-COMPLETION-DIAGNOSTICS.md)
records the unavailable result; it does not establish a new unlock or fallback.

An earlier 617.42 attempt at a loaded point reporting GPU VID 1195 mV was
refused by the controller FB ceiling guard before any write; the later attempt
used a 1000 mV GPU hold. GPU VID and controller FB are separate readings.
Neither result establishes a board-specific safe ceiling.

**Common Apply, profile replay and Reset were not exercised on hardware:**
verification did not succeed. They have mocked coverage only. The final
hardware-free suite passed **1649 tests**, including renderer checks. These
results are scoped to the tested board, drivers and operating points; controller
identification does not imply that writes will work on another board. See
[the Ada validation record](../ADA-VALIDATION.md#up9512r-i2c-discovery-and-verification)
for the driver-switch incident and final restoration scope.

## Raw response capture on both drivers

A later bounded entry trace positively captured the response to one unchanged
`0A=00` WriteEx request on each of 581.42 and 617.42. Each driver's known
supersurface response caller supplied phase `0`, I2C category `1`, write
operation `0`, raw status byte `03`, and translated RM status `0x16`; NVAPI
returned `-1`. A successful identity-read response validated the same observation
path before each write capture. This supersedes the earlier uncertainty about
whether a raw rejection response could be observed.

The specific firmware policy predicate and a supported unlock remain unknown.
The captures do not establish a controller password requirement, a BIOS bit to
clear, or an accepted write. All seven controller registers remained exact after
each attempt; `39` and `2A` were never written. The round added two explicit
unchanged-byte requests and no direct research MMIO requests. Two driver switches
completed without a reboot request. Independent readback confirmed the original
state after restoring 617.42; the tracer was removed, research services stopped,
nvtunedrv running, and the verified EXE reopened. The monitored interval contains
no new crash/TDR/dump-error event and no event-query errors. See the
[raw-completion evidence](https://github.com/Thermetery-Technology-Co-Limited/drutadrv/blob/ada-up9512r-bar0-probe/research/ADA-RAW-I2C-COMPLETION.md) for exact binary bindings, capture checks,
and the remaining interpretation limits. Application write support is unchanged.
